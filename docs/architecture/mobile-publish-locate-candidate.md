## 已证实根因

旧 `locate()` 写入状态触发页面重建，却将 `isPrefetchingFloors` 保持为 false；目标遮罩的逐帧调度因目标尚不在当前窗口，再次调用 `locateFloor()`。每次请求都递增 `_requestEpoch`，使之前的返回过期。慢响应时产生不断自我失效的定位请求。

`thread_publish_locate_test.dart` 通过真实详情页打开编辑器、提交、等待 25 帧，故意延迟目标窗口返回。旧实现一次发布产生多个同目标 GET，断言失败（`publish-locate-before.log`）；候选相同用例通过。此前即时返回的假仓储测试没有覆盖这个竞态。

## 候选行为与边界

- 发布成功后，以确认响应中的主题、子贴和楼层 ID 启动一次显式读取，不先刷新详情、默认窗口或逐页探测；正文只取服务端真实目标窗口，不伪造分页或计数。
- 独立导航代次合并同目标在途请求，连续发布、切换页面／子贴／身份丢弃旧结果。编辑已加载楼层继续原位更新。
- 定位期间显示简短“已发布”提示，旧内容、返回和发表入口仍可用。失败停止自动尝试，“重试定位”只重读 GET，不重复 POST。
- 窗口布局后仅对齐一次，不等待图片、字体或固定稳定计时。用户拖动或主动导航让出控制，未完成时保留“查看新楼层”入口。
- 筛选外目标仅沿既有 `40010` 规则清作者筛选并重读目标。403 撤权清空旧正文，已发布事实与读取失败分开。
- 现有深链／数字导航继续保留；其目标读取也设置在途状态，避免页面重建重发。此轮不全面改写其他定位入口。

紧急候选已知限制：移除发布后的前置详情刷新后，目录／筛选栏的总层数仍可能显示旧详情计数，手动刷新后同步；正文与目标窗口使用最新服务端结果。后续已授权的统一定位切片须补齐定位完成后的非阻塞统计同步，不能推导或伪造总数，也不能再次把详情刷新作为显示新楼层的前置条件。

代码责任拆分：`thread_published_floor_navigation.dart` 管理确认后的读取生命周期；`thread_published_floor_reading.dart` 管理非阻塞反馈与一次布局对齐；详情页只连接会话、路由及操作。原详情页与控制器超过 700 行，已按本次新增职责拆出独立对象，不使用 `part` 机械搬移。
