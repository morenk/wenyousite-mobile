# 富文本跨端稳定性专项实施计划

状态：阶段 0 首轮跨端只读审查完成，阶段 1 待实施；2026-09-10 已汇总 Windows 与 VPS 证据。本文件是实施与验收计划，不是新协议，也不代表新增行为已经交付。

## 1. 目标、范围与成本约束

保留 Flutter Quill、现有 Web 编辑器和完整 Markdown 持久化，不批量迁移历史正文，不引入第二份权威正文，不在本专项增加复杂样式或更换视觉体系。

覆盖使用富文本正文的创建、编辑、阅读、草稿、剪贴板及后端保存路径；各业务入口是否使用同一链路在阶段 0 核实，不能把纯文本模块直接纳入富文本协议。

验收目标：

1. 文字、Unicode 空白、段落、样式、链接和业务节点身份不被意外改变。
2. 相同上下文中的相同编辑动作产生约定结构；屏宽造成的自动折行不改变内容。
3. 规范化首次收敛后稳定；多次跨端保存不继续增加转义、空行或隐藏 marker。
4. 编辑与阅读结构一致，排版遵循 Foundation；不要求不同设备逐像素一致。
5. 不可安全转换、未知节点、冲突及异步失败不覆盖原正文或最后一份有效草稿。

本轮交付边界为：可追溯基线、问题状态、阶段计划和首批共享用例提案。协议文件、生成客户端、应用源码与线上行为保持不变。

## 5. 实现切片顺序

1. 回车、正文段落、可见空段、引用分段：统一结构识别与映射，保留已经验收的手动 Enter 对齐行为。
2. 行内格式与字面输入：固定样式区间、格式边缘空白、转义及组合；只有回归证据充分后才简化来源属性。
3. 原子节点：提及、骰子、表情和图片的身份、光标、删除、复制和阅读布局。
4. 剪贴板、撤销和草稿：事务边界、异步返回、选区迁移、提交前 flush 和最后有效快照。
5. 历史、未知结构与版本能力：确定可读但不可编辑内容的处理，避免编辑其他文字时意外降级。

列表语义和空格式块当前已有独立调查，先接收其已提交结论，不在本任务平行修改。缺少已提交契约时，只整理用例提案与证据，不在客户端先行发明协议。

## 6. 工程改进原则

- 中立模型负责文字、marks、块边界和节点身份；Quill 适配层负责操作与位置映射。逐块减少“模型→字符串→再次猜结构”，不一次替换整个 Codec。
- 同一端的阅读、编辑与复制尽量共用语义识别；两端不必共享运行代码，但必须共享规范和独立预期。
- 后端做确定的合法性校验和规范化，不猜测用户按键来源。HTTP revision 变化不等于正文语义变化，差异需逐文件核实。
- 新内容写法收敛，历史兼容限定输入形态并有负向用例。未知原意不自动补格式，不从旧 LF 推断 Enter/Shift+Enter。
- 手输 Markdown 符号保持字面；合法站内粘贴的结构恢复先验证入口，进入正常文档后逐步评估能否统一序列化，不直接删除现有保护属性。
- 格式组合在命令入口约束，编码出口继续防守；不能通过放松安全校验让无法往返的组合“保存成功”。

## 7. 用例、诊断与质量门禁

共享用例应包含来源、规则版本、初始 Markdown、无歧义选区、操作步骤、独立语义预期、规范写法和能力前置条件。详细提案见首批矩阵。测试语义摘要仅用于验收，不上传为正文，不写数据库，也不保存光标/撤销栈作为正文协议。

分三层：真实问题回归；有界边界组合；在前两层稳定后增加有固定 seed 的合法随机操作与失败缩减。已经存在的回归直接复用，不为数量复制测试。

至少覆盖：Web 创建→后端保存→移动编辑→后端保存→Web 重开，以及相反方向。分别断言文字、空段、段落、marks、节点、选区和视觉结果；编解码幂等不能替代独立语义断言。

诊断链为：原始输入→编辑结构→操作后结构→提交 Markdown→后端返回→阅读结构。默认只记录用例 ID、版本、阶段、规则和错误类型；正文仅使用已确认脱敏的复现样例，不自动采集真实用户或私信内容。正常业务 API 不因诊断增加临时字段。

各端接入自己的既有质量入口。移动端高风险契约/持久化切片执行 `npm run check`，涉及依赖、Android 或交付安装时构建 Debug APK；文档审查阶段只执行相关文档和 diff 检查。协议生成变更必须独立同步并核对生成 diff。

## 8. 兼容、发布与回退

- 区分协议版本、fixture revision、实现 commit 与部署 SHA；不为每个 Bug 增加协议版本。
- 新节点、既有语义改变、不可逆写入需要明确兼容评审；读支持和未知内容保护先于写开放。
- 回退验证包括“旧实现读取新写入”，不能只证明旧进程能启动；无法安全回退时停止相关写入口并保留内容，具体操作另行授权。
- 负责人授权合并与发布之前只交付任务分支、PR 和候选，不部署、不晋级、不打正式 Tag。
- 验收记录必须绑定源码、包名、版本、APK SHA-256；ADB 安装按 AGENTS 核对设备实际应用，不把构建号相同视为同一安装包。

## 10. 下一批可直接执行的切片

### S1-A：补齐 newline 跨仓一致性检查

责任端：VPS Backend/Web；不改 fixture 内容、编辑行为、OpenAPI 或数据库。把 newline 加入既有真实文件比较，并测试：文件相同通过；仅 newline 被修改时失败；错误能指出仓库和文件；其他原清单继续有效。故障注入只使用临时测试文件或隔离 checkout，不污染主仓共享语料。旧门禁漏检、候选能检出的证据必须保留。缺失参考仓库沿用既有运行环境约定，不在本切片静默扩大或放松门禁。

交付：各仓独立任务分支、相关工具回归、文档说明与 PR；不部署、不要求移动端重建 APK。跨仓改动按已提交 commit 交接，不复制未提交目录。

### S2-A：验证 Web 编码失败后的提交保护

责任端：VPS Web。先使用真实 ThreadCreateForm + MilkdownEditor/Crepe 和 bridge，在正文 A 成功同步后注入下一次序列化失败，继续输入 B；保存接口可 mock，编辑器不得换成 textarea 替身。断言编辑器仍保留 B、显示失败、保存草稿和发布均不调用 mutation、不提交旧 A；恢复编码并成功编辑后提交当前正文。对其他富文本表单使用同一错误通道的情况作范围审查。

若注入证明有缺口，先记录为异常路径缺陷候选，再在同一行为切片增加提交阻断与恢复；没有实际用户触发输入时，不声称已复现用户丢稿或已解决原问题。若现有实现全部通过，提交测试及结论，不为证明假设而改变断言。

S1-A/S2-A 不依赖新产品语义，可先推进；其余矩阵补充由后端正式契约切片发布后，两端再消费。
