# 图片服务端耗时分析

本报告是本次图片上传体验候选的验收证据，不是运行状态事实源。复查时重新运行采集脚本；运行状态以健康接口、`/api/v1/meta` 和后端运维文档为准。

## 采集方法与边界

- 通过已配置的 `wenyou-admin-vps` 身份只读访问 `wenyousite-image-worker.service` 的 journal；没有变更权限、重启、部署、修改数据或上传测试媒体。普通 `wenyou-dev` 身份不能读取系统 journal。
- 时间窗口为 `2026-09-13T20:01:03Z` 至 `2026-09-20T20:01:03Z`，精确时间见 `server-timings.json`。
- 采集时 `/api/v1/meta` 的 `buildSha` 为 `fc88ea09a808af9c54c1f5b971e116b3be4a471b`。这是采集时运行版本，不能据此认定七天内所有样本均来自该提交。
- 统计 261 条具有完整阶段字段的成功处理完成日志。不是全部上传尝试、失败率或唯一用户数；历史测试和真实使用无法从这些字段区分。分位数使用 nearest-rank。
- 仅保留用途、是否动图、阶段时长与时间戳；不保留媒体 ID、对象 key、URL、用户、请求正文或凭据。
- `observedStagesTotalMs` 对每条记录先求已记录阶段之和，再计算分位数；不将各阶段 p95 相加。该值不含客户端压缩、客户端直传、HTTP 确认、客户端轮询发现延迟及未记录开销，因此不代表端到端等待时间。
- 没有 batchId、批次图片数及客户端来源，不能可靠区分单张和九张，也不能把这些数据全部归为移动端。单图/九图对照应由客户端确定性调度回归及负责人真机验收补充，不能从相邻时间戳猜测。

### 关键事实

1. 正文静态图校验 p95 为 35ms；常见等待并非全花在安全校验。界面“安全处理中”覆盖排队、下载、校验、转码、产物上传等不同操作。
2. 主要范围内静态图的队列 p95 为 6–9ms。本样本不支持优先无条件增加 Worker 并发；评论有一次 11420ms 排队长尾，仍需继续观察。
3. 静态图回传存储存在明显长尾：正文最长 77330ms，评论最长 90129ms。现有日志只能定位到该阶段，不能直接判定是存储商、网络、SDK 重试还是连接管理问题。
4. GIF 的 `displayMs` 包含 `ensureAnimationDisplay` 内编码、存储上传与数据库发布事务，不能当成纯 CPU 编码时间。正文 GIF 最长 53262ms，需要下一切片拆分这些耗时后才可选择优化点。
5. 本轮客户端释放传输名额、允许继续编辑、使用本地预览，可减少强迫等待和前图阻塞后图；不改变上述服务端每张图片处理耗时，不能将这份基线冒充上线后性能提升。

## 后续服务端切片建议

优先为存储调用补齐按操作统计的耗时、重试次数与安全错误分类，并将动图 display 编码、上传、发布事务分开计时；基于同一版本和固定样本比较。不得记录签名 URL、key、用户或请求正文。

随后再决定是否优化连接与超时/重试、WebP 编码 effort、排队策略或衍生图流水线。保持当前安全检查、动态图语义和 `COMPLETED` 产物完备要求。本轮没有实施这些服务端变化，也不通过提前标记完成隐藏处理时间。

## 复现采集

在 Windows 从本目录执行：

```powershell
Get-Content -Raw ./collect-media-timings.py | ssh -o BatchMode=yes wenyou-admin-vps python3 -
```

脚本只读既有七天日志并在远端内存中聚合，仅输出脱敏记录。复查结果以其自身窗口与采集时 SHA 为准。
