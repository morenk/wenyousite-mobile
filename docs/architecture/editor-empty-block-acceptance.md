## 根因核对

根因不在按钮，而在编辑状态、Markdown 语法和阅读语义之间的约定不完整：

1. 写出器允许空列表，但中立块解析和富文本行解码各自的列表正则要求非空正文。此前标题修复分别修改了两处标题正则，没有统一空块定义，也没有用格式状态矩阵覆盖列表。
2. 空格和 Tab 是用户真实输入，原转换却会把它们当成标题／列表／引用标记后可忽略的语法空白；居中／居右的纯空白行又沿用有正文的对齐保存规则，触发拒绝保存。
3. 单行往返成功不代表上下文正确：空 `-` 紧邻正文或嵌套列表时可能成为 Setext 标题下划线；嵌套有序列表的两空格映射还可能使独立阅读器丢掉一个空列表项。原 Codec 的两套解析逻辑对此可能一起误判。

候选将标题／列表的识别和前缀写出收敛到 `MarkdownEditableBlockSyntax`，将行属性白名单、冲突检查与块写出集中到 `MarkdownDeltaBlockEncoder`。真实输入的纯空格／Tab 使用对应字符引用保存，不添加占位文字；空白对齐只保留为当前编辑会话的输入状态，不写入不合法对齐标记。可见性检查仍把这些空白判为空正文。

空列表在必要的源码分隔后写出，解码时不把这道语法分隔变成额外可编辑空行；已有 Setext 标题保持阅读语义。除完整 Delta 语义往返检查外，对包含空列表的保存新增独立 Markdown 阅读校验，核对全部列表项和空项数量；父项自身的空内容与子项文字分别统计，不一致时保留编辑内容并阻止覆盖。

## 已证实的跨端剩余问题

输入 `1. 甲\n  1. 乙\n    1. 丙`，移动端旧映射视为三层；删空「丙」后，即使按新规则在空项前加入语法空行，独立 Markdown 阅读仍可能只有两个列表项。两个空格一级是现有移动端实现假设；共享夹具只固定了嵌套无序列表样例，尚未完整定义嵌套有序列表、混合列表及空项的列宽规则，需要关联 VPS 任务核对 Web 与后端并补齐契约。

此候选不在缺少共享夹具时单独另定有序列表的缩进规则；已用回归固定上述丢项输入必须拒绝保存的保护。运行时数量校验不能识别所有“项数相同但层级不同”的历史有序列表，不能替代后续完整层级映射修正。本问题不能用放宽往返校验或修改测试预期为丢失内容来掩盖。普通有序／无序空列表及受现有契约支持的嵌套无序空项与此分开验收。
